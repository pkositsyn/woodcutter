# woodcutter — порт cutting.py на Go

Дата: 2026-07-02

## Цель

Переписать `cutting.py` (оптимальный 1D-раскрой, cutting stock) на Go со
стандартной раскладкой `cmd` + `internal`, **без внешних LP-библиотек** (симплекс
и branch & bound пишутся вручную). Финал — тесты, доказывающие эквивалентность
Go- и Python-решений.

## Что делает исходный алгоритм

Оптимальный раскрой при нескольких типах исходных досок с ограниченными запасами.
Минимизируется суммарная длина использованного материала. Метод — генерация
столбцов Гилмора-Гомори:

1. LP-релаксация мастер-задачи (минимизация суммарной длины материала) → duals.
2. Прайсинг через ограниченный рюкзак (bounded knapsack, DP с бинарным
   разложением) → новые паттерны раскроя.
3. Итерации, пока reduced cost < −tolerance.
4. Целочисленная задача (ILP) на найденном пуле паттернов → план раскроя.
5. Парсинг stdin (`склад --- требования`), детальный текстовый отчёт.

## Решения по дизайну

### LP-решатель: двухфазный tableau-симплекс

- Плотная матрица. Фаза 1 (искусственные переменные) → допустимый базис;
  фаза 2 → оптимизация.
- Duals извлекаются из строки целевой функции по столбцам slack/surplus.
- Знаки duals воспроизводят PuLP: `y_i ≥ 0` (спрос, `>=`), `z_k ≤ 0` (запас,
  `<=`), чтобы формула reduced cost `stock_len[k] − y·a_j − z_k` совпадала.
- ILP — branch & bound поверх того же симплекса.
- Отклонённые альтернативы: Big-M (численная нестабильность), revised simplex
  (overkill для наших размеров).

### Раскладка пакетов

```
go.mod                       module github.com/pkositsyn/woodcutter
cmd/woodcutter/main.go       чтение stdin, вызов солвера, печать отчёта
internal/lp/                 симплекс (LP) + branch&bound (MILP), duals
internal/knapsack/           bounded knapsack (порт DP с бинарным разложением)
internal/cutting/            генерация столбцов, сборка плана
internal/cutting/parse.go    парсинг «склад --- требования»
internal/cutting/report.go   текстовый отчёт (чище оригинала)
reference/cutting.py         вендорная копия оригинала (entry-point под __main__)
reference/gen_golden.py      генератор golden из pulp-решения
internal/cutting/testdata/   входы *.txt + *.golden.json
```

### Поток данных

`stdin` → `parse` → `Requirements`, `Stock` → `cutting.Solve()`:

1. агрегация склада по длине, фильтр требований длиннее макс. доски;
2. стартовые жадные одно-типовые паттерны;
3. цикл генерации столбцов: `lp.Solve` релаксации → duals → `knapsack.Solve`
   прайсинг по каждому типу доски → добавление улучшающих паттернов. Порядок и
   условия добавления — **точно как в Python**, чтобы пул паттернов совпадал;
4. `lp.SolveMILP` (branch & bound) на финальном пуле → целочисленное решение;
5. сборка `CuttingPlan` (доски, куски, пропилы, отходы) → `total_material`.

### CLI-паритет

- Формат stdin идентичен оригиналу: секция склада, разделитель `---`, секция
  требований; строки `длина[, количество]`.
- Текстовый отчёт — чище/структурированнее оригинала (логика раскроя та же).

## Тестирование

Критерий эквивалентности (согласован): **совпадение `total_material` +
валидность плана**.

- `internal/lp`: юнит-тесты на малых LP с известным оптимумом и duals; MILP
  против brute-force на мелких целочисленных задачах.
- `internal/knapsack`: против brute-force на случайных мелких инстансах
  (детерминированный seed).
- `internal/cutting` — кросс-проверка с Python:
  - `reference/gen_golden.py` один раз прогоняет тот же pulp-алгоритм на всех
    `testdata/*.txt`, пишет `*.golden.json` (`total_material`). Коммитим —
    CI не требует python.
  - Go-тест на каждом кейсе: `total_material` Go == golden **И** план валиден
    (спрос удовлетворён, запас не превышен, куски+пропилы влезают в доску).
  - Кейсы: один тип доски; много типов; неограниченный запас (большое число);
    недостаток запаса (`-1`); требования длиннее доски (отброс); пустые секции;
    padding=0.

## Риск

ILP на пуле паттернов — эвристика, оптимумы неуникальны. Для совпадения
`total_material` буквально копируется control-flow генерации столбцов из Python.
Расхождение на кейсе — сигнал для разбора, не повод подгонять тест. Валидность
плана проверяется независимо в любом случае.
