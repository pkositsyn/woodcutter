# MILP branch-and-cut с best-bound (ускорение целочисленного solve)

Дата: 2026-07-02

## Проблема

На патологическом входе (8 взаимно простых длин требований) целочисленный
solver `lp.SolveMILP` не завершается сам: он **находит** оптимум, но не может
**доказать** оптимальность и крутится до `MILPTimeout`/дефолтных 30 с. Для
пользователя это «зависание».

Эмпирика (вход из `terminate_test.go`, padding=4):

| | Результат | Время |
|---|---|---|
| Python (PuLP→CBC) | 171600 (оптимум) | 1.1 с, завершается сам |
| Go, timeout 2 с | 172200 (хуже) | обрыв по дедлайну |
| Go, timeout 15 с | 171600 (оптимум) | обрыв по дедлайну |
| Go, timeout 60 с | 171600 | не завершается сам |

Разбивка Go по фазам: генерация столбцов — **14 мс** (7 итераций, 74 паттерна);
целочисленный solve — упирается в дедлайн. Корневая LP-релаксация даёт
`171491.8`, целочисленный оптимум — `171600`.

### Корень проблемы

Наивный branch & bound в [internal/lp/lp.go](../../../internal/lp/lp.go)
(`SolveMILP`) складывает две беды:

1. **Слабая нижняя граница.** Единственное отсечение — `ceil(LP) ≥ incumbent`.
   Корневая LP-граница (171491.8) далеко под оптимумом (171600), поэтому
   отсечение почти не срабатывает и дерево ветвления взрывается.
2. **Каждый узел решает симплекс с нуля**, а ветвление добавляется
   *строками-ограничениями*; ветка `>=` тянет surplus+artificial → снова
   нужна фаза 1. Один узел стоит как полное решение задачи.

CBC быстр за счёт отсекающих плоскостей (поднимают границу), warm-start dual
simplex и эвристик. Мы воспроизводим первое и третье (варианты **B + D**),
оставаясь без внешних зависимостей. Warm-start (вариант C) сознательно **вне
объёма** этой работы.

## Цель

Целочисленный solver должен **доказывать оптимальность и завершаться сам**,
задолго до дедлайна, на текущих golden-входах и на hard-входе из
`terminate_test.go`. Дедлайн и лимит узлов остаются страховкой (backstop).

Не-цели: warm-start / revised simplex; per-node отсечения (только задел под
них); произвольные не-целочисленные цели (bound опирается на целочисленность
цели, как и сейчас).

## Решения по дизайну (из брейншторма)

- **Контракт:** доказанный оптимум + backstop. При срабатывании backstop —
  вернуть лучший допустимый инкумбент, пометить как недоказанный (gap > 0).
- **Отсечения:** цикл Gomory-отсечений **в корне**, затем best-bound B&B без
  новых отсечений. API спроектировать так, чтобы per-node отсечения можно было
  добавить позже.
- **Граница пакетов:** вся работа с tableau/slack и отсечениями — внутри `lp`.
  `cutting` только читает флаги результата.
- **Отчёт:** в норме без изменений; строку про недоказанность печатать
  **только** если сработал backstop.

## Архитектура

Затрагиваются: `internal/lp/lp.go` (основная работа), точечно
`internal/cutting/{types,solve,report}.go`, плюс тесты.

### Компонент 1 — экспонирование tableau (внутри lp)

Выделить внутренний `solveTableau(p Problem) (*tableau, Status)`, который решает
LP и **сохраняет** финальный tableau, базис и метаданные колонок:
- вид каждой колонки: структурная / slack / surplus / artificial;
- отображение slack↔исходное ограничение (для обратной подстановки).

Публичный `Solve` (извлечение x/duals) и генератор отсечений строятся поверх
`solveTableau`. Внешнее поведение `Solve` не меняется — существующие
`lp_test.go` / `milp_test.go` проходят без изменений.

Тип `tableau` (внутренний, не экспортируется): строки, `basis []int`,
`colKind []colKind`, `slackOfCon map[int]int` (или обратное), `total int`.

### Компонент 2 — генерация Gomory-отсечений

`gomoryCuts(tab *tableau, integer []bool) []Constraint` (внутренний):

Для базисной структурной переменной `x_B` с дробным значением, из строки
tableau `x_B + Σ_j a_j·x_j = b` (j — нонбазисные) выводим дробное отсечение
Гомори:

```
Σ_j frac(a_j)·x_j ≥ frac(b),   frac(v) = v − floor(v)
```

Нонбазисные `x_j` включают структурные и slack/surplus. Подставляем
slack/surplus обратно через определения ограничений
(`s_k = d_k − r_k·x` для `≤`; `e_k = r_k·x − d_k` для `≥`; artificial ≡ 0 в
оптимуме, исключаются) → получаем валидное неравенство **в пространстве
структурных x**, возвращаемое как обычный `Constraint` (тип `GreaterEqual`).

На корне подстановка однозначна (slack ↔ исходное ограничение 1:1). Тот же
механизм обобщается на будущие per-node отсечения (branch-границы — тоже
ограничения).

**Численная защита (главный риск-фактор):**
- отсекать только по строкам с дробностью базиса в `[cutFracTol, 1−cutFracTol]`
  (напр. 0.01);
- коэффициенты по модулю < `cutCoeffEps` обнулять;
- отбрасывать отсечение, если носитель пуст, `frac(b)` ~0, либо динамический
  диапазон коэффициентов слишком велик (плохая обусловленность);
- лимит раундов отсечений `maxCutRounds` (напр. 15) и общий лимит числа
  добавленных отсечений;
- целочисленность LP-значений проверять с допуском (существующий 1e-6).

Bland-правило в симплексе уже даёт анти-циклинг.

### Компонент 3 — корневой цикл отсечений

Внутри `SolveMILP`, до ветвления:

```
p := problem
for round := 0; round < maxCutRounds; round++ {
    tab, st := solveTableau(p)
    if st != Optimal { break }         // передаётся наверх как есть
    if целочисленно по integer[] { return как доказанный оптимум }
    cuts := gomoryCuts(tab, integer)
    if len(cuts) == 0 { break }
    p.Constraints = append(p.Constraints, cuts...)
    // стоп также при стагнации границы между раундами
}
```

На выходе — усиленная задача `p` и сильная корневая граница.

### Компонент 4 — best-bound branch & bound (D)

DFS-рекурсию заменить min-heap (`container/heap`) узлов, ключ = LP-граница узла.

- **Узел:** накопленные branch-ограничения (`extra []Constraint`) поверх
  усиленного корня + граница-ключ (родительская LP-граница для упорядочивания).
- **Цикл:** pop минимальной границы → `solveTableau`/`Solve` → если LP не
  Optimal, отбросить; прунинг `ceil(LP) ≥ incumbent − eps`; если целочисленно
  и лучше — обновить incumbent; иначе выбрать дробную переменную (most-fractional,
  как сейчас) и добавить два дочерних узла с bound-ограничениями (`≤ floor`,
  `≥ ceil`), ключ = текущая LP-граница.
- **Доказательство оптимума:** очередь пуста, либо минимум границы в очереди
  `≥ incumbent` → incumbent доказан.
- **Backstop:** внутри цикла проверять `nodes >= milpNodeLimit ||
  (deadline и time.Now().After(deadline))`. При срабатывании — вернуть текущий
  incumbent с `Proven=false` и `LowerBound` = минимальная граница в очереди.

### Компонент 5 — primal-эвристика (D)

`roundingHeuristic(x []float64, integer []bool, p Problem) (feasible bool, obj float64, sol []float64)`:
округлить целочисленные переменные дробного LP-решения **вверх** (спрос `≥` с
неотрицательными коэффициентами остаётся выполнен), проверить ограничения
запаса `≤`; если выполнены — допустимый инкумбент, вернуть цель. Запускать
после корневого цикла (и опционально на узлах). Даёт сильный инкумбент сразу →
агрессивный прунинг. Корректность держится на B&B; эвристика — только ускоритель
(её результат всегда перепроверяется границей).

### Компонент 6 — сигнал результата

Расширить `lp.Solution`:
- `Proven bool` — оптимальность доказана (норма);
- `LowerBound float64` — доказанная нижняя граница на момент завершения.

При норме `Proven=true`, `LowerBound == Objective`. При backstop —
`Proven=false`, `LowerBound` < `Objective`, gap = `(Objective − LowerBound) /
Objective`.

### Компонент 7 — интеграция в cutting и отчёт

- [types.go](../../../internal/cutting/types.go): в `Plan` добавить
  `Proven bool` и `LowerBound int` (округлённая нижняя граница материала).
- [solve.go](../../../internal/cutting/solve.go): прокинуть `sol.Proven` /
  `sol.LowerBound` в `Plan`. Существующая логика `sol.Status != lp.Optimal →
  infeasible` сохраняется (best-effort инкумбент возвращается со `Status=Optimal`,
  но `Proven=false`).
- [report.go](../../../internal/cutting/report.go): если `!plan.Proven` —
  печатать строку вида `⚠ оптимальность не доказана (backstop); верхняя оценка
  отклонения от оптимума: X%`. В норме отчёт без изменений.

## Тестирование

- **`TestSolveHardInputTerminates`** усилить: теперь ожидаем `plan.Proven==true`,
  `plan.TotalMaterial==171600` (питоновский оптимум) и `elapsed` существенно
  меньше бюджета (напр. < 2 с, при `MILPTimeout` как backstop).
- **Golden-кросс-чеки** (`report_test.go`, `solve_test.go`,
  `testdata/*.golden.json`) — проходят без изменений (те же оптимумы).
- **Новые unit-тесты в `lp`:**
  - валидность Gomory-отсечения: отсекает дробную LP-точку, не режет ни одной
    целочисленной допустимой точки (на малом явном примере);
  - best-bound доказывает оптимум на нескольких малых MILP против брутфорса;
  - путь `Proven=false`: при крошечном дедлайне возвращается допустимый
    инкумбент с `LowerBound < Objective`.
- **Опционально:** добавить hard-вход в golden-набор как зафиксированную
  эквивалентность с Python-референсом.

## Риски и запасной план

Главный риск — численная хрупкость Gomory-отсечений на плотном float-tableau
(та же причина, по которой в исходном дизайне отвергли Big-M). Митигируется
фильтрами из Компонента 2 и лимитом раундов.

Если отсечения окажутся ненадёжными для доказательства оптимума на hard-входе в
бюджете, best-bound + primal-эвристика (D) сами по себе резко сокращают дерево и,
вероятно, докажут оптимум; отсечения — акселератор, а не единственная опора.
Критерий приёмки проверяется эмпирически против 171600.

## Вне объёма

- Warm-start / revised simplex (вариант C).
- Per-node отсечения (только совместимый API-задел).
- Целевые функции с нецелой оптимальной стоимостью.
